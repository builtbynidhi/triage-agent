# 0005. Policy retrieval: hybrid search with cross-encoder reranking

- Status: accepted (the decision was the project owner's, from the measurements)
- Date: 2026-11-20
- Phase: 4
- Evidence: [docs/retrieval.md](../retrieval.md), generated by `pnpm eval:retrieval`

## Context

The spec asks for hybrid retrieval: FTS5 keyword search and vector search, merged by reciprocal rank fusion, with the top 10 reranked down to 4. We measured 13 configurations (keyword only; three local embedding models, each alone and in hybrid with no reranker, a term-coverage heuristic, or a local cross-encoder) on two question sets:

- **27 eval-derived questions:** the raw ticket text of every eval case, one question per required clause.
- **32 held-out questions:** short, customer-style questions, committed before anything was measured.

The two sets disagree:

| hit@4                                                         | Raw tickets (eval-derived) | Short questions (held-out) |
| ------------------------------------------------------------- | -------------------------- | -------------------------- |
| Keyword only                                                  | 40.7%                      | 71.9%                      |
| Vector only, bge-small                                        | **70.4%**                  | 93.8%                      |
| Hybrid, bge-small, no rerank (the pre-registered rule's pick) | 59.3%                      | 87.5%                      |
| **Hybrid, bge-small, cross-encoder rerank**                   | 51.9%                      | **96.9%**                  |

The selection rule written before measuring ("best eval-derived hit@4 among hybrid configurations") picks hybrid with no reranker. That configuration is worse than vector-only on _both_ sets, and it is not the pipeline the spec describes.

**Re-measured 2026-11-22**, after `delivery.estimates` gained a definition of remote locations: every number in the table is unchanged except the no-rerank hybrid, which moved by one question per set to 55.6% / 84.4%. The decision stands. The table above keeps the evidence as it was when the decision was made.

## Decision

`search_policy` uses **hybrid search with `bge-small-en-v1.5` embeddings, RRF (k = 60), and the `ms-marco-MiniLM-L-6-v2` cross-encoder reranking the fused top 10 down to k**. The configuration lives in `packages/data/src/retrieval/defaults.ts`.

The tool description tells the agent to send **one short, specific question per call**, never the pasted ticket, and to search twice for a ticket with two questions.

## Why

- The agent never searches with the raw ticket: it writes its own query. The held-out set (short, specific questions) is the closer model of those queries, and on it this configuration is the best measured: 96.9% hit@4 and 75% hit@1 (joint best).
- It is the spec's pipeline. The reranker is the stage that turns "the right clause is somewhere in the top 10" into "it is in the top 4 the agent reads".
- Vector-only is better on raw tickets, so the tool description shapes queries away from raw tickets, toward where this configuration wins.

## Honest costs

- **The held-out set is no longer a clean confirmation.** It was meant to confirm a choice made on the eval-derived set; instead it informed this one. Phase 7 is the real check, because it measures retrieval with the agent's actual queries.
- **Latency:** about 37 ms per search, against about 3 ms for vector only. The cross-encoder reads 10 query and clause pairs. That is negligible beside a model call (seconds), but it is real.
- **Models:** two local downloads of about 30 MB each, cached in `.cache/models` (and in CI). No API, no cost.

## Revisit when

- **Phase 7 shows the agent's queries look like raw tickets.** Then switch to vector-only: it is one line in `defaults.ts`, measured here.
- **Policies, the embedding model or the reranker change.** Re-run `pnpm eval:retrieval`, and record the change here or in a new ADR.
